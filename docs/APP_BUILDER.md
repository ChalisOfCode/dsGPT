# Building apps in dsGPT 0.7

Install the desktop update over the existing dsGPT installation. Keep your existing data folder and model registrations. The installer preserves them. The bundled phone app uses your existing dsGPT signing identity; it can update through the existing wireless-debugging connection, or you can install the APK manually.

Open **Work**, choose your installed local model (including your abliterated model), paste the full request, and send it. Say **Android APK**, **Windows EXE**, or **both** so the requested outputs are clear. Include the screens, interactions, recovery behavior, permissions, settings to preserve, and examples you care about. Screenshots may be attached. You do not need to split a large request yourself.

The first app task prepares the reviewed build tools automatically if the existing Docker image is missing or outdated. Docker Desktop must be running in Linux-container mode. This downloads public tools and dependencies once; it does not upload your request or project. Progress appears in the Work history and tool setup status. If Windows or Docker needs a restart, resume the task afterwards.

The builder saves the original request, reads every section, and maintains a project checklist. Source files, compiler logs, and reference text are read in pages that fit the model context. Follow-up changes are retained with the original request. Pause a task before editing its request, then resume. Initial requests and follow-ups allow up to 1,500,000 characters in storage; the combined project specification has the same limit. This is not a claim that a model can reason over that much text simultaneously.

Supported automatic recipes are Android Kotlin/Compose with SDK 35, Gradle 8.13 and the pinned scaffold dependencies, and native Windows C++17 GUI applications. Other frameworks or additional dependencies may require extending the reviewed tool image. Generated code runs offline in isolated Linux containers. Host automation, Bluetooth hardware, phone permissions and Windows audio routing require appropriate implementation and testing on the actual device.

The model starts from a reviewed scaffold, implements features, adds tests, builds, reads failures and repairs individual code regions. Completion requires the requested artifact types and current-source build/test receipts, plus its review of every specification section. The checklist is an agent review, not proof of complete functionality. Empty or trivial tests can still pass; inspect important behavior on your phone or PC.

Android builds run unit tests and lint, then verify alignment and signing. A project-specific development signing key is retained in the local dsGPT database and used in a separate signing container, outside generated Gradle scripts. Keep a backup of the dsGPT data folder: losing that key prevents future updates of the same generated app. These are development APKs, not Play Store releases. Windows builds run portable feature tests and cross-compile a PE executable; they are not Authenticode-signed. Neither recipe claims a physical-device run.

When a task finishes, download its APK/EXE and project export from Work. The export includes source, the exact requirements and the requirements-review record. Check the recorded test results and any remaining device checks before relying on an app. If a build blocks, keep the task and its log, explain the correction in the follow-up box, and resume; do not start over unless you want a separate app identity.

Your RTX 3080 Ti still runs the same local model. This update improves the process around it; it does not retrain it or make it as capable as a hosted frontier model. The current model stays warm for five minutes between turns; switching models releases the previous dsGPT-used Ollama model. Larger prompts take more review turns, and complex applications can still require correction or a stronger model. No paid inference service is added.
